第 1 堂

建立筆記系統

解決長時間任務中「Claude 忘記早上交代的規則」。

一句話記住規則只講在對話裡會被壓縮掉；寫進檔案，每次都會重新載入。

背景知識

Token 與上下文視窗

Token 是模型計算文字量的單位，實際數量依模型而定，不必背換算公式，用 /context 直接看用量即可。上下文視窗是 Claude 在一次對話中「同時看得到」的全部內容：系統提示、CLAUDE.md、讀過的檔案、工具輸出與對話。

視窗大小標準 200K Token；Opus 4.6 以後、Sonnet 4.6、Sonnet 5 等支援 1M（依方案）
每次新對話都是全新視窗，上一次的內容不會自動帶過來
最佔空間讀檔與工具輸出（安裝日誌、測試輸出）
查看用量/context

官方文件：Explore the context window ↗

自動壓縮（Auto-compact）

對話接近上限時，Claude Code 會把整段對話整理成結構化摘要取代逐字記錄，讓工作繼續。摘要保留需求、決策、改過的檔案、錯誤與待辦；完整工具輸出與中間推理會消失。

內容壓縮後
專案根目錄 CLAUDE.md、沒有 paths 的 rules從磁碟重新注入
Auto memory（MEMORY.md）、Plan mode 的計畫從磁碟重新注入
有 paths 的 rules、子目錄 CLAUDE.md再讀到相符檔案時重新載入
最近修改的檔案重讀最多 5 個
已呼叫的 Skill 內容重新注入（每個上限 5,000 Token）
只在對話中講過的規則只剩摘要，可能遺失
重點遺忘的主因不是「舊對話被刪掉」，而是「規則只存在對話裡」。
  • /compact 聚焦在 Repository 規則：壓縮時指定要保留的重點
  • /autocompact：調整自動壓縮的觸發門檻
  • /clear：換到不相關的工作時清空對話

Context Rot（上下文衰退）

輸入越長，模型運用其中資訊的穩定度越差。Chroma 在 2025 年 7 月的技術報告測試 18 個模型，發現表現會隨輸入變長而非均勻下降，干擾資訊越多越明顯。所以就算換成 1M 視窗，只放當下需要的資訊仍是最穩的做法。

實作步驟

步驟 1：用 /init 產生初版 CLAUDE.md

在專案根目錄啟動 Claude Code 後輸入 /init，Claude 會分析專案寫出建置、測試指令與慣例，再由你補上看程式看不出來的規則。

步驟 2：整理 CLAUDE.md（建議 200 行內）

CLAUDE.md

## 指令
- 安裝：npm install
- 測試：npm test

## 架構原則
- 採三層架構：Controller → Service → Repository
- 資料庫查詢只能寫在 src/repositories/
- 輸入驗證寫在 src/services/，Controller 不做驗證

## 工作方式
- 每完成一個項目，更新 progress.md

## 目前進度

情境問答

Claude 到下午開始不照 Repository Pattern 寫，要怎麼處理？
  • 確認規則是否寫在 CLAUDE.md 或 .claude/rules/，而不是只在對話裡講過。
  • 用 /context 確認檔案真的有載入。
  • 長任務中主動 /compact 聚焦在架構規則，或換任務時 /clear。
  • 如果一定不能違反，加上 lint 規則或 CI 檢查（第 4 堂的強制機制）。
CLAUDE.md 已經寫到 400 行，Claude 好像越來越不照做？
  • 官方建議每個 CLAUDE.md 在 200 行內，太長反而降低遵守度。
  • 只跟特定目錄有關的規則，拆成有 paths 的 rules。
  • 多步驟的做法搬到 Skill（第 2、3 堂），需要時才載入。
  • 刪掉 Claude 看程式碼就知道的內容（目錄結構、套件清單）。
同事說：「我的 Claude 記得要用 pnpm，你的怎麼不記得？」

那是 auto memory，存在各自電腦的使用者目錄，不會同步給別人。團隊共同規則要寫進專案的 CLAUDE.md 並提交到 git。

要找出整個專案哪裡還在用舊 API，怕把上下文塞爆？

請 Claude「用 subagent 調查」。子代理在自己的上下文中讀檔，最後只回傳摘要，主對話保持乾淨。

第 2 堂

建立 API 規範 Skill

解決「每支 API 回應格式、狀態碼、驗證方式都不一樣」。

一句話記住只有做某類工作才需要的詳細做法，做成 Skill；需要時才載入全文。

背景知識：什麼是 Skill

Skill 是一個資料夾，裡面的 SKILL.md 教 Claude「某件事該怎麼做」，也可以放範例、範本與腳本。它採漸進式載入：

  1. 對話開始時，只載入每個 Skill 的名稱與 description。
  2. Claude 判斷任務相關，或你輸入 /api-standards 時，才載入 SKILL.md 全文。
  3. 輔助檔（如 examples/）只有 SKILL.md 指示、且需要時才會讀。
寫法description 要寫清楚「做什麼、什麼時候用」，關鍵用途放前面；description 加 when_to_use 超過 1,536 字元會被截斷。　官方文件：Extend Claude with skills ↗

CLAUDE.md、rules、Skill 怎麼分工

機制適合放載入時機
CLAUDE.md每次都要知道的事：指令、架構原則每次對話開始
.claude/rules/只跟特定路徑有關的規則每次，或讀到相符檔案時
Skill特定任務的詳細做法、範例、流程需要時才載入全文

問題：API 細節不一致

API實際回應（示意）
GET /api/employees{ code: 200, data: [...], message: "success" }
POST /api/employees{ success: true, payload: {...} }
DELETE /api/employees/:id{ deleted: true, id: 1 }

另外還有：新增成功回 200（應為 201）、驗證有時寫在 Controller 有時寫在 Service、測試只測成功情況。

---
name: api-standards
description: 員工系統 REST API 規範。實作或修改 API 端點、設計回應格式、
  撰寫 API 測試時使用。定義回應格式、狀態碼、驗證位置與測試要求。
paths:
  - "src/**/*.js"
  - "tests/**/*.js"
---

# API 開發規範

## 1. 回應格式
- 成功（200、201）：{ "code": 200, "data": { ... }, "message": "success" }
- 失敗（4xx、5xx）：{ "code": 400, "data": null, "message": "...", "errors": { ... } }
- errors 只在欄位驗證失敗時提供；錯誤訊息不可包含 SQL 或堆疊追蹤

## 2. 狀態碼
- 200：GET、PUT、DELETE 成功（本專案 DELETE 不使用 204）
- 201：POST 新增成功
- 400 驗證失敗 · 401 未登入 · 403 無權限 · 404 不存在 · 409 資料衝突 · 500 伺服器錯誤

## 3. 輸入驗證
- 驗證寫在 Service 層，Controller 不做驗證、不碰資料庫
- 順序：必填 → 格式 → 唯一性 → 業務規則 → 呼叫 Repository
- 唯一性除了先查詢，資料庫也必須有 UNIQUE 限制；寫入衝突同樣回 409
- 範例：examples/employee.service.js

## 4. 測試要求
- 每支 API 至少測：成功、400（必填／格式）、409（重複）、404（不存在）
- 每個測試前清空測試資料，測試之間不可互相依賴
- 範例：examples/employee.test.js
舊版錯誤舊版在這裡寫了 allowed-tools: Read, Write, Grep, Bash。這個欄位的意思是「呼叫此 Skill 的那一回合，列出的工具不用詢問」，不是限制。規範型 Skill 不需要執行指令，應刪除。
204 的矛盾HTTP 規定 204 No Content 不能帶回應內容，和「所有回應都用統一格式」衝突。擇一：DELETE 回 200，或回 204 並在規範中註明為例外。錯誤格式可參考 RFC 9457 Problem Details ↗。

步驟 3：範例檔（驗證寫在 Service）

examples/employee.service.js
async function hireEmployee(input) {
  const errors = {};
  if (!input.name) errors.name = '姓名必填';
  if (!input.email) errors.email = '信箱必填';
  if (!input.department) errors.department = '部門必填';
  if (Object.keys(errors).length) throw new ValidationError(errors);

  if (!EMAIL_RE.test(input.email)) {
    throw new ValidationError({ email: '信箱格式不正確' });
  }

  if (await employeeRepository.findByEmail(input.email)) {
    throw new ConflictError('信箱已被使用');
  }

  try {
    return await employeeRepository.create(input);
  } catch (err) {
    // PostgreSQL 唯一鍵衝突：資料庫 UNIQUE 是最後防線
    if (err.code === '23505') throw new ConflictError('信箱已被使用');
    throw err;
  }
}
controllers/employeeController.js
async function createEmployee(req, res, next) {
  try {
    const employee = await employeeService.hireEmployee(req.body);
    res.status(201).json({ code: 201, data: employee, message: 'success' });
  } catch (err) {
    next(err);   // 交給共用 errorHandler 轉成 400／409／500
  }
}

情境問答

我沒下指令，Claude 卻自己開始跑 /add-api 的流程？

流程要讀很多檔案，會不會把主對話塞滿？

commands 與 skills 裡剛好有同名檔案，會用哪一個？

Skill 優先。建議刪除舊的 commands 檔，避免有人改錯檔案。

第 4 堂

設定外部系統連接與安全防線

解決「推送與建 PR 靠手動」，同時避免 AI 把機密推上去或直接改到 main。

一句話記住讓 Claude 能推送之前，先用 permissions、Hooks、分支保護把關。

背景知識

Claude Code 可以直接操作 GitHub

Claude Code 透過 Bash 執行 git、npm、gh。只要安裝並登入 GitHub CLI（gh），就能直接 gh pr create。舊版說「無法建立 PR」並不正確，真正要處理的是認證與權限範圍。會不會先詢問你，取決於權限模式：Manual 模式除了唯讀指令都會詢問；Pro、Max、Team 方案的預設起始模式是 auto，由分類器審查（見「補充觀念」）。

permissionssettings.json 的 allow／ask／deny，比對順序 deny → ask → allow，deny 一定優先

步驟 5：PreToolUse Hook：推送前檢查

.claude/hooks/guard-git.js
const { execSync } = require('child_process');

let raw = '';
process.stdin.on('data', (c) => (raw += c));
process.stdin.on('end', () => {
  const input = JSON.parse(raw);
  const cmd = (input.tool_input && input.tool_input.command) || '';
  const isPush = /\bgit\s+push\b/.test(cmd);
  const isCreatePr = /\bgh\s+pr\s+create\b/.test(cmd);
  if (!isPush && !isCreatePr) process.exit(0);   // 其他指令放行

  const branch = execSync('git branch --show-current').toString().trim();
  if (isPush && (branch === 'main' || /[\s:]main(\s|$)/.test(cmd))) {
    console.error('禁止推送到 main，請改用 feature 分支並建立 PR。');
    process.exit(2);                               // 2 = 阻擋
  }
  try {
    execSync('npm test', { stdio: 'pipe' });
  } catch {
    console.error('npm test 未通過，已阻擋。請先修正測試。');
    process.exit(2);
  }
  process.exit(0);
});
.claude/settings.json（與 permissions 並列）
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "node \"$CLAUDE_PROJECT_DIR/.claude/hooks/guard-git.js\"",
            "timeout": 300
          }
        ]
      }
    ]
  }
}
  • Hook 從 stdin 收到 JSON，指令在 tool_input.command；stderr 訊息會回傳給 Claude。
  • 另一種寫法：exit 0 並輸出 JSON 的 permissionDecision: "deny"。
  • Hook 回傳 allow 也推翻不了 deny 規則。用 /hooks 檢查是否載入。
  • Windows：有安裝 Git Bash 時，Hook 預設以 bash 執行，上面的寫法可直接使用；沒有 Git Bash 時會改用 PowerShell，建議改成 "command": "node", "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/guard-git.js"] 的寫法。
  • Hook 以你的帳號權限執行，加入前要檢查內容。Hooks guide ↗

---
description: 測試通過後，建立分支、commit、push，並建立 Pull Request
argument-hint: <分支名稱> <PR 標題>
arguments: [branch, title]
disable-model-invocation: true

  - Bash(git switch *)
  - Bash(git add *)
  - Bash(git commit *)
---

# 送出變更：$title

- 分支：!`git branch --show-current`
- 變更：!`git status --short`

1. 執行 npm test，未通過就停止並回報。
2. 檢查 git diff，確認沒有 .env、金鑰、node_modules、建置產物。
3. 若目前在 main，執行 git switch -c feature/$branch。
4. 逐一 git add 本次相關檔案，不要用 git add . 或 -A。
5. 以 Conventional Commits 格式 commit（例：feat: add POST /api/employees）。
6. git push -u origin 目前分支
7. gh pr create --base main --title "$title"，內文含變更摘要與測試結果。
8. 回報 PR 網址，不要合併。

自我測驗

情境問答

Hook 寫好了，Claude 還是照樣 push 到 main？
  • 檢查程式是否用 exit 2（exit 1 不會擋）。
  • 用 /hooks 確認 Hook 有載入，matcher 是 Bash。
  • 確認 Hook 讀的是 stdin JSON 的 tool_input.command。
  • 最後防線：GitHub 分支保護，伺服器端直接拒絕。
deny 已經寫了 git push * main，為什麼還不夠？

規則是字串比對，git push origin HEAD:main、先 cd 再推等寫法可能比對不到。所以要 permissions、Hook、分支保護三層一起用，任何一層漏掉還有下一層。

想讓同事在 PR 留言就請 Claude 修改，怎麼做？

在專案執行 /install-github-app 完成設定後，在 PR 或 Issue 留言 @claude 加上需求即可。留言者需對儲存庫有寫入權限。

MCP 的 Token 可以直接寫在 .mcp.json 裡嗎？

不建議。.mcp.json 會提交到 git，Token 會外洩。用 ${GITHUB_PAT} 環境變數，並使用有到期日、只限特定儲存庫的 fine-grained PAT。

  • 程式只推到分支、開 PR，合併前一定有人看過。
專業版
  • 以 gh 完成 GitHub 認證（gh auth setup-git），避免明文憑證；SSH 採 Ed25519 並啟用 passphrase。
  • permissions 依 deny → ask → allow 評估，deny 不可被 allow 或 Hook 覆寫；字串比對需以縱深防禦補強。
  • PreToolUse Hook 以 exit 2 或 permissionDecision: "deny" 阻擋；伺服器端以 branch protection／required checks 收斂。
  • 擴充：遠端 GitHub MCP（HTTP、環境變數注入 fine-grained PAT）、claude-code-action（@claude）、Plugin 分發。
補充觀念

用得穩、用得安全的六個觀念

四堂課建好了架構；這一頁補上日常操作時最常影響結果的機制：權限模式、先規劃、回溯、自我驗證、安全與自動化。

一句話記住先知道 Claude 現在「能不問就做什麼」，再給它可以自己檢查對錯的方法。

1. 權限模式：Claude 什麼事不用問你

權限模式決定 Claude 哪些動作可以直接做。第 4 堂的 permissions 規則是疊加在模式之上的細部設定。

模式不用問你就能做適合
plan讀取、探索；提出計畫，不改原始碼先了解程式再動手
Manual（default）只有讀取敏感工作、想逐一審查
acceptEdits讀取、編輯檔案、常見檔案指令（mkdir、mv、cp 等）一邊看一邊改
auto大部分動作，由另一個分類器模型在背景審查長任務、減少一直按確認
dontAsk只有預先允許的工具，其餘直接拒絕CI、腳本
bypassPermissions全部只限隔離的容器或 VM
常見誤解「Claude 每個指令都會先問我」不一定成立：Pro、Max、Team 方案的預設起始模式是 auto，由分類器審查，不是每次都問你；Enterprise 方案與 API 金鑰才是 Manual。組織管理員可用 managed settings 的 disableAutoMode 關閉 auto。
  • 互動中按 Shift+Tab 切換；啟動時可用 claude --permission-mode plan 指定。
  • deny 規則在所有模式都有效，包括 bypassPermissions；這也是第 4 堂先設 deny 的原因。
  • 以 root 身分或在個人電腦上不要用 bypassPermissions，它只適合用完即丟的隔離環境。

每送出一則提示，Claude Code 就建立一個檢查點。按兩下 Esc（輸入框為空時）或輸入 /rewind，可以選擇：

Summarize from here／up to here把某段對話壓縮成摘要，騰出上下文
限制不會還原：Bash 指令改動的檔案、多數子代理的修改、你在 Claude Code 外手動改的檔案。檢查點不取代 git。Checkpointing ↗

5. 安全：提示注入與機密

提示注入是指網頁、Issue、文件或 MCP 回傳的內容裡夾帶「給 AI 的指令」，企圖讓 Claude 做你沒要求的事。

  • 不要把不受信任的內容直接丟給 Claude；核准指令前看清楚內容。
  • 網路指令（curl、wget）預設不會自動核准；不需要時可加進 deny。
  • WebFetch 在獨立上下文處理網頁內容；新的專案與 MCP 伺服器第一次使用時需要你確認信任，但 -p 無人值守模式不會做這個確認。
  • 只使用自己寫或可信任來源的 MCP 伺服器；Anthropic 不稽核第三方 MCP。
  • 機密不要進上下文：deny Read(./.env)；需要更嚴格隔離時用 /sandbox 限制檔案與網路存取。
  • 分支送出前可執行 /security-review 做一次安全檢查。

6. 無人值守：claude -p

claude -p 以非互動方式執行，用在腳本、pre-commit 或 CI；第 4 堂的 GitHub Actions 也是同樣的機制。

終端機

第一句

第二句

5-2　加上 PreToolUse Hook（exit 2）

預期
被 Hook 擋下，Claude 會轉述「禁止推送到 main，請改用 feature 分支並建立 PR。」遠端不變。（已實測）
補充
實測中 Hook 比 permissions 規則先執行：同時設定時，git push origin main 會先被 Hook 攔下。

5-3　故意做錯：把 exit 2 改成 exit 1

把 guard-git.js 裡兩處 process.exit(2) 改成 process.exit(1)，做一個新 commit，重新啟動後再試一次（Manual 模式下出現確認時請核准）。

影響：你以為有防線，其實沒有；未審查的程式直接進 main。
怎麼發現：檢查 Hook 程式的 exit code，並像本關一樣實際測一次。

改回 exit(2)。

整體收穫

白話版
  • 記得住：重要的事寫在檔案裡，Claude 每次開工都會重新看。
  • 做得一樣：把團隊做法寫成手冊（Skill），寫程式時自動照著做。
  • 不跳步：把固定步驟做成按鈕（/add-api），每次照同一套 SOP。
  • 守得住：危險動作用門禁擋下，程式一定經過 PR 與人工審查。
  • 用得穩：先知道現在是哪種權限模式；大改動先規劃；給 Claude 測試讓它自己檢查。
  • 親眼看過：LAB 裡 Hook 回 1 就擋不住、換個寫法就繞過規則，所以防線要多層。
  • 最重要的一句：寫在文件裡的是「提醒」，真正要擋的要用程式。
專業版
  • 狀態外部化：以 CLAUDE.md、條件式 rules、@import 狀態檔與 auto memory 對抗 compaction 與 context rot。
  • 規範封裝：以漸進式揭露的知識型 Skill 承載領域規範，降低常駐上下文成本。
  • 流程顯式化：以參數化、禁止模型自動觸發的流程型 Skill 定義 SOP。
  • 確定性邊界：permissions（deny 優先）＋ PreToolUse Hooks（exit 2）＋ branch protection 構成縱深防禦。
  • 操作治理：權限模式決定基線授權（Team 起始為 auto，deny 跨模式有效）；Explore→Plan→Implement；以可執行檢查形成驗證閉環；checkpoint 不涵蓋 Bash 副作用。
  • 實證：LAB 實測 Hook 先於 permissions 執行、exit 1 不阻擋、deny 字串可被 HEAD:main 繞過，驗證縱深防禦的必要性。
  • 架構原則：Predictable AI = External State ＋ Explicit Routing（Skills）＋ Hard Boundaries（Hooks & Permissions）。

建議導入順序

  1. 第 1 週：/init 建立 CLAUDE.md；同時設定 permissions deny（禁止讀 .env、rm -rf、推 main）與 main 分支保護。基本防線成本低，越早越好。
  2. 第 2 週：盤點最常被糾正的規範做成知識型 Skill；把固定流程做成 /add-api、/ship。
  3. 第 3 週：加入 Hooks；需要時再接 GitHub MCP 或 GitHub Actions。每位成員完成一次第 5 堂 LAB。
  4. 穩定後：把 skills、hooks、MCP 設定打包成 Plugin，一次分發給全組。
